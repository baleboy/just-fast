# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Fastino** — a free, minimal iOS intermittent-fasting tracker. SwiftUI + SwiftData, iOS 26.4 minimum, Xcode 26.x. Bundle id `com.baleware.fastino`.

Two documents drive the work and are the source of truth; keep them current:
- `specification.md` — product & technical spec. Source files reference its sections (`§2`, `§4.6`, …) in their header comments; keep those references accurate when editing.
- `IMPLEMENTATION.md` — what's built vs. deferred. The Lock Screen *rectangular* and Home Screen widgets are the only things still deferred; the watchOS app, both widget extensions and CloudKit sync all ship.

## Commands

```bash
# Build
xcodebuild build -scheme Fastino -destination 'platform=iOS Simulator,name=iPhone 17'

# iOS widget extension (Lock Screen widget + Control Center control). Worth
# building on its own: it catches Shared/ code that doesn't compile under
# app-extension rules before an app build hides it.
xcodebuild build -scheme 'Fastino WidgetsExtension' -destination 'platform=iOS Simulator,name=iPhone 17'

# Watch app. The target name really is doubled — the wizard appended "Watch App"
# to a product name already ending in it. Only the target name is affected; the
# bundle is com.baleware.fastino.watchkitapp and it displays as "Fastino Watch App".
xcodebuild build -scheme 'Fastino Watch App Watch App' \
  -destination 'platform=watchOS Simulator,name=Apple Watch Series 11 (42mm)'

# Unit tests (swift-testing)
xcodebuild test -scheme Fastino -destination 'platform=iOS Simulator,name=iPhone 17' -only-testing:FastinoTests

# A single suite or test (swift-testing names, not XCTest)
xcodebuild test -scheme Fastino -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:FastinoTests/CurrentStreakTests
xcodebuild test -scheme Fastino -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:FastinoTests/CurrentStreakTests/threeConsecutiveDaysEndingToday
```

The app opens on `SplashView` for ~1.4s (§5), so **anything driven from `simctl` has to account for it** — either pass `-noSplash` (DEBUG only) or wait it out before taking a shot. Launch with `-seedDemo` (DEBUG only) to populate a streak plus an active fast for screenshots; `-seedEating` seeds the between-fasts state instead. `-tab stats` / `-tab history` / `-tab settings` (DEBUG only) opens straight onto another tab — the custom tab bar can't be tapped from `simctl`, so this is how the other screens get screenshotted. `-fixtureHealth` backs the Stats screen's Health panels with `FixtureHealthProvider` rather than HealthKit (a simulator's Health store is empty and its permission sheet can't be tapped); add `-noHealthData` to see their empty states, and `-seedHistory` for three months of fasts. `-syncDiagnostics` opens the sync diagnostics sheet straight from launch, since it's behind a Settings row and `simctl` can't tap. They live in `DebugLaunch` in `RootView.swift`. Two more, for the App Store pass only, live in `Shared/Support/ScreenshotFlags.swift`: `-noSyncWarning` hides the "iCloud sync is off" row (a simulator is never signed in to iCloud, so it's always shown there and always wrong), and `-healthPanelsFirst` draws the Health panels above the bento so `simctl` can see them — which is why the "hoist `HealthPanels` and put it back" workaround below is no longer needed for that shot. Note the panels sit *below* the bento and the week strip, so `simctl` — which can't scroll — only sees the top of them; to look at the whole section, temporarily hoist `HealthPanels` to the top of `StatsView.content` and put it back afterwards.

Only the iOS 26.5 simulator runtime satisfies the 26.4 deployment target — installing on the iOS 26.1 devices fails. Same on the watch: the target is watchOS 26.5, so only the **watchOS 26.5** simulators work.

`simctl` can't tap, so the watch's *active* fast state is unreachable on a booted watch sim — the `#Preview`s at the bottom of `WatchTimerView.swift` are how it gets looked at (via Xcode, or the `RenderPreview` MCP tool).

The Xcode project uses **file-system-synchronized groups** — new `.swift` files are picked up automatically; no `project.pbxproj` edits needed. **Which folder you put a file in decides which platforms build it**: `Shared/` compiles into every target, `Fastino/` is iOS-app-only, `Fastino Widgets/` is the iOS widget extension only, `Fastino Watch Widgets/` the watch one. Put anything that touches UIKit, the tab bar, or a full-size screen in `Fastino/`; put model/engine/store/design code in `Shared/`. The split is by folder rather than by membership exceptions precisely so the default for a new file is correct. **`Fastino/` is not compiled into either extension**, so an intent a widget or control runs must live in the extension's own folder or in `Shared/` — `Fastino/Intents/FastIntents.swift` is unreachable from there.

## Architecture

Three layers, deliberately separated so the logic is testable and reusable by the deferred widget/watch targets:

Paths below are relative to `Shared/` unless they start with `Fastino/`.

**1. Pure core — no SwiftData, no globals, no I/O**
- `Model/FastRecord.swift` — `Sendable` value snapshot of a fast (id/start/end/goalHours). Everything analytical operates on `[FastRecord]`, never on `@Model` objects.
- `Engine/FastingEngine.swift` — streaks, goal days, 7-day strip, 30-day averages. Every function is a pure function of `[FastRecord]` + `now` + `TimeZone`.
- `Engine/FastValidation.swift` — `end > start`, 7-day cap, overlap (touching endpoints allowed, open fast extends to `.distantFuture`), `excludingID` for edits.

Keep this layer pure. New stat/validation logic goes here and gets unit tests in `FastinoTests/FastingEngineTests.swift` (swift-testing `@Suite`/`@Test`, ~35 tests).

**2. Persistence + the single write path**
- `Model/Fast.swift`, `Model/AppSettings.swift` — SwiftData `@Model`s. **Every attribute must have a default and there are no unique constraints** — this keeps the schema CloudKit-compatible. Preserve that when adding fields.
- `Store/AppContainer.swift` — the shared `ModelContainer` (plus `inMemory()` for previews/tests). Mirrors to the CloudKit private database, naming `iCloud.com.baleware.fastino` explicitly rather than using `.automatic` — see `Sync/` below and IMPLEMENTATION.md.
- `Sync/` — the two rules CloudKit forces on us: `OpenFastMerge` (two devices each start a fast offline) and `SettingsElection` in `Model/AppSettings.swift` (duplicate settings rows). Both pure and unit-tested; `SyncReconciler` applies the merge, `CloudSyncStatus` reports whether sync actually works (started by *both* app entry points, and surfaced in iOS Settings **and** watch Settings).
  - `SyncLog` is the one observer of `NSPersistentCloudKitContainer.eventChangedNotification`; `CloudSyncStatus` and `RemoteChangeRefresher` subscribe to it rather than registering their own, keeping their original filters. It keeps the last 50 events — **including ones still in flight**, which is the state that actually diagnoses a stuck import — plus a marker for every `FastStore` write, in the app group's `UserDefaults` (event metadata only, never fast data). **When sync is under suspicion, this is the tool**: `docs/sync-testing.md` is the procedure, and both apps carry a DEBUG-only diagnostics screen (iOS Settings → General, or launch with `-syncDiagnostics`; watch Settings). The pure ring buffer is unit-tested in `FastinoTests/SyncLogTests.swift`.
  - **The wait is a window, not a launch.** One opens on launch (`SyncTiming.launchImportTimeout`, 15s) *and* on a resume from ≥30s in the background (`resumeImportTimeout`, **45s — measured**: a phone-started fast reached a backgrounded watch on resume in ~30s). It was 6s first, guessed on the reasoning that an already-set-up container imports quickly; that produced the worse failure — "Checking", give up, claim "Ready", contradicted twenty seconds later. **A wait that expires before the answer arrives is worse than no wait at all.** Past the deadline the wait continues while an import is genuinely running (`isImportInFlight`, bounded by `maxImportDuration` so a completion that never arrives can't hang it) — the timeout is a floor for "nothing ever started", not a ceiling on a slow import. This is what recording in-flight events buys. A watch that's been in a pocket for an hour knows exactly as little as one that just launched, and **the resumed app is the case users actually report**: a cold launch imports as part of mirroring setting itself up, while a resume gets no setup and depends on a silent push that may never have arrived. `markBackground()` ignores all but the first call, because `scenePhase` passes through `.inactive` on the way back in as well as out. Every resume is logged as an **App active** event, so "does an import follow a resume?" is answerable by reading the event list.
  - **The watch says "Checking iCloud…" for the length of the open window** when it has no open fast and no import has landed yet — a store that hasn't imported and a store with genuinely no fast look identical from the view, and on watchOS the first import routinely lands seconds after launch. Saying "Ready" and then contradicting it is what makes sync *feel* broken on the occasions it works. The Start button stays enabled throughout (a standalone watch mustn't wait on a network; a race just makes two open fasts, which `OpenFastMerge` collapses), and a device that's signed out or offline skips the wait entirely. `WatchTimerView(checkingOverride:)` forces either state for the previews — a preview process opens the real mirrored container, so the ready preview would otherwise sit on "Checking" for the whole timeout.
  - **A CloudKit import is not a local write**, so it runs none of `FastStore`'s side effects. `RemoteChangeRefresher` re-runs them on a completed `.import` — and both apps also call `refresh()` on foreground. Without it, a fast ended on the phone leaves the watch's goal notification armed and the **complication counting up forever**: `WidgetCenter` reloads are device-local, so the phone's `reloadAllTimelines()` never reaches a watch face, and the complication's timeline policy is `.never`.
- `Store/FastStore.swift` — **the only place fasts are mutated.** UI, App Intents, and the future widget/watch targets all go through `startFast`/`endFast`/`toggle`/`addManual`/`update`/`delete`. Each method validates, saves, reconciles notifications, and calls `WidgetCenter.reloadAllTimelines()`. Never write to a `Fast` from a view or an intent directly — add a method here instead.
  - `endFast` returns a `FastActionResult` carrying the celebration facts (goal met, new longest fast/streak, current streak) so the UI can decide what to animate.

**3. Surfaces**
- `Fastino/Views/` — `RootView` is the four-tab shell (Timer / Stats / History / Settings) with the custom `FlameTabBar`, which labels the tabs with SF Symbols; the names live on as accessibility labels. **The timer's flame is filled while a fast runs and an outline between fasts** (`FlameTab.symbol(fasting:)`) — the bar is a status light as well as a control, which is the one thing the mascot itself couldn't do at 21pt, where its eyes would be 2pt and half its life is spent as a flat muted tint. VoiceOver gets the state as the tab's accessibility *value*. All four tabs stay mounted behind each other, so a tab keeps its scroll position and sheets across a switch — **and its `task`/`onAppear` run at launch whether or not it's selected**, which is why anything that prompts the user reads `\.flameTabIsVisible` first (`HealthPanels` does; without it the Health sheet greets you on the splash screen). Plus `TimerView` (home: `FlameRing` + mascot + zone beads + start/end), `StatsView`, `SettingsView`, `HistoryView`, `HealthPanels` (the Apple Health section §4.8, embedded at the foot of `StatsView` rather than on a screen of its own), `EditFastView`, `AdjustTimeSheet`, and `SplashView` (§5) — the launch mark, plus the `BalewareMark`/`BalewareLockup` publisher lockup. **The splash is a sibling inside `RootView`'s stack, not a wrapper around it in `FastinoApp`**: `.preferredColorScheme` is applied in `RootView`, so a splash above it follows the system scheme and flashes the wrong palette for anyone who overrode it. It falls on a timer, never on loading work — the store opens synchronously — so nothing may be made to block on it. **The Baleware wordmark is the one text in the app that isn't Baloo 2**; it walks baleware.com's own font chain (`UIFont(name:)` probing, since an unresolvable `Font.custom` silently yields the system face), and the six-stripe rainbow is fixed in both schemes because it's someone else's mark.
- `Fastino Watch Widgets/FastingComplication.swift` — the watch complication (§4.7), in the `Fastino Watch WidgetsExtension` target. Reads the store **read-only through the app group**, with mirroring off — extensions are separate processes, so the store lives in `group.com.baleware.fastino` and every target must declare it (a target missing it silently gets its own empty container rather than erroring). Its timeline schedules every instant the display changes — hour marks, zone boundaries, the goal — because the label is a whole-hour count; refreshes otherwise come from `FastStore.reloadWidgets()` on the watch itself, or from `RemoteChangeRefresher` after a CloudKit import. It branches on `widgetRenderingMode`: faces render accented/vibrant and discard colour, Smart Stack gets `.fullColor`. **The mascot's face is punched through the body**, not drawn in ink, for the same reason — flattened to one tint, ink would be flame-on-flame.
- `Fastino Widgets/` — the iOS widget extension (§4.5): the Lock Screen `.accessoryCircular` widget and the **Control Center toggle**. Almost nothing lives here — the entry, store read, timeline instants, colour rules and the circular gauge are all in `Shared/Widgets/`, shared with the complication. Two rules that bite:
  - **The control's `SetFastingIntent` writes from the extension process**, through `AppContainer.writableShared()` — the one exception to "the app owns writes", and still not a second CloudKit mirror. It reaches CloudKit via persistent history when the app next runs. Don't make it `openAppWhenRun`; a toggle that launches the app is not a toggle.
  - **A control is not a timeline.** `WidgetCenter` never touches it, so `FastStore.reloadWidgets()` also calls `ControlCenter.shared.reloadControls(ofKind:)`, and the app-side counterpart is `RemoteChangeRefresher`'s `.NSPersistentStoreRemoteChange` observer plus its `mainContext.rollback()` — without the refault, a control tap leaves `TimerView` stale until relaunch. Kind strings live in `FastinoWidgetKind` and **must never change once shipped**: the system stores them against every placed widget and control.
  - **No confirmation on the control**, deliberately — unlike `ToggleFastIntent`, which confirms because Back Tap fires by accident.
- `Fastino Watch App Watch App/` — the watch app (§4.7). `WatchRootView` is a three-page `TabView(.page)` — `[Progress] ← [Timer] → [Settings]` — opening on the timer, so the fast is always one swipe away and never behind a back button.
  - `WatchTimerView` — ring, mascot, elapsed time, zone, one button. It reuses `FlameRing`/`FlameMascot` by passing a smaller size rather than reimplementing them, and uses `Text(timerInterval:)` for the digits so Always-On stays correct without a per-second timeline.
  - `WatchSettingsView` / `WatchProgressView` / `WatchFastDetailView` / `WatchTimeEditView` — **these exist because the watch app is installable without the phone.** A standalone watch has no other way to pick a protocol or repair a record. Keep them a subset: no appearance (there's no light appearance on watchOS), no notes, no export. Anything phone-sized belongs on the phone.
  - **The open fast is listed in Progress and its start is editable**, which is the correction that matters most — tap Start twenty minutes late and every zone boundary and the goal alert are wrong from then on. `WatchTimeEditView` edits hour and minute only; the day comes from the chips. *Ending* a fast stays the timer page's job, so there's only ever one End button.
  - Watch settings edits must `AppSettings.touch()` — they bind with `@Bindable` and bypass `FastStore`, and an unstamped edit loses the election to the phone's older row.
  - **Only one device schedules notifications** — see `NotificationOwnership` under `Notifications/` below.
- `Shared/Health/` + `Fastino/Health/` — the Apple Health read path (§4.8), split across the folder boundary on purpose. `Shared/` holds the pure half: `HealthSample` (the value types), `SleepAggregator`, `WeightSeries`, and the `HealthProvider` protocol with its `FixtureHealthProvider`. `Fastino/Health/HealthKitProvider.swift` is **the only file in the app that imports HealthKit**, and it's iOS-only by placement.
  - **Nothing from Health is ever persisted.** HealthKit data may not be synced to iCloud and `AppContainer` mirrors to CloudKit, so a `@Model` or an app-group cache would be a violation, not an optimisation. It's fetched per screen and held in memory.
  - **Sleep is a union, not a sum** — two trackers reporting the same night would otherwise read as sixteen hours. `inBed`/`awake` excluded; unknown future values fall through to not-asleep so a new OS can't silently inflate totals.
  - **A night is then reassembled from its pieces** (`SleepAggregator.nightGap`, 3h). A watch scores brief awakenings all night, so the union leaves one night as a dozen stretches; anything resumed within the gap is the same sleep, anything later is a new one. The day's *main* sleep is the group with the most sleep in it — not the widest span, so a long restless afternoon can't outrank the night. **`mainSleep*` is not the longest unbroken stretch**: it was, and that drew every eight-hour night on the chart as a two-hour smear at a random offset. `FixtureHealthProvider` now emits fragmented spans through the real aggregator for exactly this reason — it used to hand over finished `SleepNight`s, which is why no preview could show the bug.
  - **The fasting/weight panel is by the calendar week** — `FastingEngine.weeklyAverageHours` for the bars, `WeightSeries.weeklyMean` for the line, both bucketed by `FastingEngine.weekStart`, so a week's fasting and that week's weight are one column. **Not a rolling daily mean**: that still draws one column per day, so the picture reads daily however it was averaged. Bars average the days that *have* a fast (matching `weightVsFasting`), leave a fastless week absent rather than zero, and exclude the open fast — a part-measurement would drag the week down. The weight point is the week's mean, not its last reading.
  - **`weekStart` is the one locale-aware piece of date maths in the engine** — which day a week starts on is the user's own convention, so it reads `Calendar.current.firstWeekday`, with the parameter pinned in tests. Everything else stays on `dayNumber`.
  - **The shared date domain is snapped out to whole weeks** (`HealthPanels.domain`) and the x grid lines stride by `.weekOfYear`. A week-wide bar hanging off a mid-week edge is drawn over the axis labels rather than clipped, and both panels' grid lines have to agree.
  - **A night belongs to the day you woke**, matching the goal-day rule, which is what makes it line up with the fasting bars for free.
  - **`SleepNight` carries both *how much* and *when*** — the total asleep, plus the start and end of the night's **main** sleep. The scatter plots the **total** (`hours`) — "how much did I sleep" is the question, and a nap after a short night is part of the answer. `mainSleep*` is no longer drawn but is still computed and tested; it's what a clock-time view would need.
  - `FastingEngine.eatingStops` is the series that isn't from Health — the *start* of the fast credited to each day, i.e. when eating stopped. It's the x axis of the sleep scatter. `eatingStops` picks the longest fast per day, like `lastDays`, so the dot and the bar are the same fast.
  - **The two panels pair their series differently, and only one is dual-axis.** `fastingWeightPanel` has to be: kilograms and hours have no common unit, so it's drawn in the bars' hours scale with weight projected into it and every label converted back (`project`/`mass(at:)`, labelled through `overlayAxis`, hours on the **trailing** axis). Only the hours axis draws grid lines there, so a bar top can't be read in kilograms. `Panel` takes an optional date domain: the top panel has one and gets the week grid, the scatter passes `nil` and draws its own axes.
  - **`sleepScatterPanel` is a scatter, and has been two other things.** One `PointMark` per night: x = the clock time eating stopped, y = the total hours asleep, a dashed vertical rule at the start-time anchor (`SleepScatterScale` in `Shared/Health/`, pure and unit-tested). The question the panel exists for is whether stopping earlier goes with sleeping longer, and that's a question about two quantities — so they are the two axes. It was dual-axis first (the dots' height borrowed from the sleep scale, so the shape was an artifact of the projection, joined by a `LineMark` implying a continuity between nights that doesn't exist), then a one-clock-axis timeline of stop dots and sleep bands over thirty dated columns — honest and unreadable, because hours asleep only existed as band length and the eye can't compare that across a month. **Don't reintroduce either.** Grid lines are drawn on both axes here (`stopAxis`, `hoursAxis(values:)`), which is safe because nothing is projected. The plot is `.clipped()`, because a stop outside the scale would otherwise be drawn outside the card. Only nights with *both* a stop and a sleep are plotted. **Its one summary is `SleepSplit`** — mean hours asleep either side of the anchor (the lower median stop without one), drawn as a level across each side and as two `SplitTile`s under the chart (bento-style number tiles, not a caption — a sentence there was invisible), `nil` unless both sides have ≥3 nights. Two groups, not hour bins: an average of two nights is noise dressed as a fact. It's a pair of means and must stay one — no fit, no coefficient, no "because".
  - The stop values are signed hours from that day's midnight (evening = negative) rather than a 0–24 clock, because a wrapped axis puts 23:50 and 00:10 at opposite ends; they're drawn as they are, later to the right. `TimeFormat.timeOfDay(hoursFromMidnight:)` wraps them for the labels.
  - **The sleep axis is not zero-based** — sleep lives in 5–9h and a zero base halves the panel — and both axes tick on whole hours, chosen in `SleepScatterScale` rather than left to `.automatic`.
  - **An outlying stop doesn't set the x scale.** A 36h fast started on a Monday morning lands 16h from the credited midnight and would pile every real night into one column. `SleepScatterScale` sizes the axis from the stops near the user's median (±8h); sleep is never filtered; the outlier is still drawn and still read out.
  - **There are no correlations in the app, deliberately.** A Trends sub-screen with two scatter plots, fitted lines and generated headlines (`Correlation.swift`, `HealthCorrelation.swift`) was built and then cut for being more machinery than a fasting app's stats page wants. The panels show what happened; the user interprets. The sleep scatter is the dots from that screen without the fit or the headline, and that's where the line is: don't reintroduce a fitted line, a coefficient, or a computed claim about one series explaining another — see IMPLEMENTATION.md.
  - **There is no "denied" state to show.** HealthKit won't disclose whether reads were granted, so the UI only ever says "no data" and points at the Settings tab's **Apple Health** row. That row (`healthCard` in `SettingsView`) is the only entry point back into the permission: it branches on `hasBeenAsked()` alone, asking before the sheet has been shown and opening the Health app afterwards, because re-requesting after a refusal presents nothing and iOS Settings' page for Fastino has no Health entry. It must never claim Health is *on*. `HealthPanels` re-reads on foreground so a grant made over there shows up on the way back.
- `Fastino/Intents/FastIntents.swift` — `Start`/`End`/`ToggleFastIntent` + `AppShortcutsProvider`. Only Start/End are App Shortcuts; Siri phrases rely on the `INAlternativeAppNames` aliases in `Info.plist` ("Fasting", "Fast") so `"Start \(.applicationName)"` reads as "start fasting". `ToggleFastIntent` is deliberately *not* an App Shortcut — it stays a Shortcuts-app action and requests confirmation (it's the Back Tap target).
- `Notifications/NotificationManager.swift` — goal-reached notification (scheduled at start+goal, cancelled on end/edit), the fat-burn/ketosis milestones (12h and 14h, skipped when they'd land at or after the goal), and the start reminder (on by default, suppressed while fasting). Permission is requested lazily, never on launch.
  - The start reminder fires at the user's **start-time anchor** (`startReminderHour`/`Minute`, 20:00 by default) — the same instant the eating window closes. Since the anchor never moves it's a single repeating calendar trigger; `FastStore.reconcileNotifications` only has to arm/cancel it (it's suppressed while a fast runs).
  - **Exactly one device schedules** — `NotificationOwnership` decides which, and `add()`/`requestAuthorization()` are no-ops on the loser. iOS forwards the phone's notifications to the watch and there's no API to opt a local notification out of forwarding (identifiers are per-device, so matching ids don't dedupe), so scheduling on both would simply double every alert. **Cancelling is deliberately ungated on both** — a device that stops owning scheduling must still be able to clear what it armed. The phone always owns it; the watch takes over only on a standalone install, detected by `CompanionProbe` asking `WCSession` whether a companion app exists.
    - **A fast started on the watch cancels the phone's start reminder over WatchConnectivity** (`CompanionRelay` in `Shared/Notifications/`, `CompanionRelayTransport` on the watch, `CompanionListener` + an `AppDelegate` on the phone). CloudKit can't carry a cancellation: the reminder is a repeating trigger armed on the phone, `removePendingNotificationRequests` is device-local, and a suspended phone runs no code — so a fast started at 19:45 on the watch still drew a 20:00 "time to start your fast?". `transferUserInfo` wakes a suspended counterpart; the mirroring push doesn't reliably. **Scheduling state crosses, never a fast** — the payload is written nowhere, and the next `reconcileNotifications()` off the imported store overwrites what it armed. This is the deliberate exception to `CompanionProbe`'s "no data over WC" rule; don't widen it. Both ends log a `Watch relay` event, so the diagnostics screen answers "did the phone wake?".
    - `isCompanionAppInstalled` reads `false` until activation completes, so the default before that is **defer**. Getting this backwards doubles every alert on every paired watch; the cost of this direction is a sub-second gap on a standalone watch's first launch, closed when activation re-runs `reconcileNotifications()`.
    - In DEBUG, `-forceWatchNotifications` / `-deferWatchNotifications` force either branch — the only way to exercise the standalone path on a paired watch.
    - `FastinoApp` re-arms on launch and foreground, so a watch-started fast gets its notifications when the phone is next opened; the accepted gap is a phone left away right through the goal.
  - **No `UNUserNotificationCenterDelegate`, on purpose** — that's what makes iOS suppress alerts while the app is open, leaving the ember burst + green "Log this fast" CTA + haptic as the app-open cue (§5). Adding one silently changes product behavior.
  - `add()` fails silently when permission is denied, so failures are logged and Settings shows a "Notifications are turned off" row; `FastinoApp` re-arms everything on launch and on foreground.

## Domain rules that are easy to get wrong

- **Streaks are derived, never stored.** Any edit/delete recomputes from `[FastRecord]`.
- **A goal day is the day a completed fast *ended***, in the current device time zone. A fast spanning midnight credits the end day only. Multiple completed fasts ending the same day count once.
- **Strict streaks** — no freezes, no rest days; one calendar day with no completed fast resets to zero. `currentStreak` anchors on today, or yesterday if today isn't a goal day yet.
- **Day arithmetic goes through `FastingEngine.dayNumber(of:timeZone:)`** (calendar-day counting from the epoch), never 86 400-second math — durations stay absolute so DST can't distort them.
- **`goalHours`/`protocolID` are snapshotted at start.** Changing the protocol in Settings never applies retroactively *on its own*. The one exception is explicit: switching plans mid-fast asks, and "change this fast too" calls `FastStore.applyProtocol(_:to:)` — the only path by which a running fast's goal moves, and nothing else may call it. Completed fasts are never re-judged.
- **The eating window closes at the daily start-time anchor, not at `lastEnd + eatingHours`.** That's what stops the schedule drifting: fasting past goal shortens today's eating window instead of pushing tomorrow's start later. `eatingHours` is descriptive only and never sets the window's length, so a protocol change doesn't resize it. Two guards return `nil` (plain "Ready"): the last fast ended >24h ago, or it ran past both its goal and the anchor — the past-due case, which would otherwise count down nearly a full day.

## Design tokens

The UI is the **"Flame Friend"** design system — the fast as a little flame you keep alive. `design_handoff_fastino_flame_friend/` is the handoff it was built from; the approved screens are `4a` (timer), `6a` (eating window), `5a` (stats), `5b` (settings) in light, `7a`/`7b`/`7c` in dark ("cozy campfire night"), plus `3a` for the motion specs. The dark eating window wasn't drawn — it reuses the dark tokens over 6a's layout. Everything else in that file is rejected exploration. Apple Health is **read-only** — sleep and weight in the panels at the foot of Stats (§4.8). Writing fasts back is still a non-goal (§1): there is no fasting sample type in the SDK, and Mindful Minutes is a meditation type, not a loophole.

- `Design/FlameMascot.swift` — **the mascot, and the heart of the direction.** `BlobShape` reimplements CSS elliptical-corner `border-radius` so the silhouette matches the mock exactly rather than approximately; `FlameExpression` is the face. Colour and expression come from context (zone while fasting, intensity on a plan card), never from the mascot itself — including the face ink, which is `palette.flameInk` (warm dark in *both* schemes, because it sits on the flame, not on the page) rather than `palette.ink`. The ready-made constructors — `.inZone`, `.pilotLight`, `.lit` — are how every other screen should reach for it.
- `Design/Theme.swift` — the palette (§5), twice over: dynamic `Color`s for ordinary view code, and numeric `RGBA`/`FlamePalette` values for the ring and mascot, which interpolate between zone colours and so can't use an opaque dynamic Color. **Both schemes come from the handoff.** Dark is not a tint of light: cards become translucent warm film with no drop shadow, and everything lit — mascot, ring, bars, progress dot — earns a `glow` it doesn't have in daylight (`palette.glow` is clear in light, which is how the views branch). Peach paper, ink #4A2A1E, accent #C9502E; the gold→orange→pink zone scale drives ring, mascot and beads together; **green is reserved exclusively for success states**. Use tokens, never literal hexes, and don't introduce system blue.
- `Design/FlameChrome.swift` — `FlameBackground` (with the calmer `resting:` variant), `.flameCard()`, `FlamePrimaryButton` + `HardShadowButtonStyle` (the 3D press: cap moves down 3pt, shadow shrinks by the same, so the two always sum to the same height), `FlameToggleStyle`, `SuccessChip`.
- `Design/Typography.swift` + `Fastino/Resources/Fonts` — Baloo 2 at 600/700/800, bundled under OFL, subset to Latin, registered via `UIAppFonts` in `Info.plist`. Reach for `.flame(_:_:relativeTo:)` (scales with Dynamic Type) or `.flameFixed(_:_:)` where growth would break the layout. 800 is the default for anything that matters; nothing is lighter than 600.
  - **Don't put Baloo on a system control that lays out its own text.** `DatePicker`'s hour/minute wells size to the *system* font's metrics; Baloo 2 is taller and gets its digits cropped top and bottom. Both watch pickers are deliberately left in the system face — the app's only system-drawn text, and legible beats consistent. Labels on `Toggle`/`Button` are fine, because those size to their content.
- `Model/MetabolicZone.swift` — the three bands. Boundaries are **absolute hours (12h, 14h), not fractions of the goal**; a goal that stops short leaves a zone unreachable rather than squeezing it. The ring, the beads, the mascot's face and the milestone notifications all read from here, so they can't drift apart.
- `RootView` owns a **custom floating tab bar**, so every tab screen hides its navigation bar and draws its own title, and every scroll view pads its bottom with `.flameTabBarClearance()` — or `.flameTabBarSafeArea()` for a `List`, whose content can't be padded from the inside (`HistoryView`).
- **`FlameRing` is for the app, not the accessory surfaces.** Its gold→orange→pink sweep plus glow turns to mud at 30pt and is discarded by accented and vibrant rendering. The complication and the iPhone Lock Screen widget share one flat `Gauge` in the *current* zone's colour instead (`Shared/Widgets/FastingCircularView.swift`) — same meaning, legible at that size. **Colour there depends on `widgetRenderingMode`**, via `FastingWidgetStyle`: the Lock Screen renders `.vibrant` and watch faces `.accented`, both of which discard colour, while Smart Stack and StandBy get `.fullColor`. Check the monochrome path first on iOS — it's the common one.
- **Swift Charts is used in exactly one place — `HealthPanels`, at the foot of Stats.** Aligned bars plus a line with a real date axis, and a scatter, is what it's for. Its two panels pair the fasting bars with weight and each night's sleep with its eating stop — do not add a third series to either, or a panel showing one alone; the pairing is the point. Everywhere else the charts are hand-drawn, and the seven-day strip stays that way because it's a designed object rather than a plot. When you do reach for Charts, every colour, font and gridline still comes from `Theme` — no default Charts palette, no system blue.
- **The Stats week strip is a bar histogram, not a row of mascots.** It was flames briefly and the design moved back: bar height carries a quantity (fast length against goal), and the mascot is for mood. Don't re-cute it.
- **Never present an alert or sheet off `.constant(value != nil)`** — use `$value.presented()` (`Shared/Support/OptionalPresentation.swift`). A constant binding swallows every dismissal SwiftUI attempts, so the presentation cannot be closed by tapping outside, by swiping, or by a `.cancel` button. Confirmed on the simulator, where the plan dialog was inescapable. Related: **`confirmationDialog` silently drops its `.cancel` button** in the card presentation these screens get, which is why the plan dialog is an `.alert` — an alert draws every button it is given.
- **Haptics go through `Support/Haptics.swift`**, never `UIImpactFeedbackGenerator` directly — the watch needs `WKInterfaceDevice`. Watch haptics only play when the app is frontmost and on-wrist, so never make a cue the user needs depend on one landing.
- **`Theme.dynamic` resolves statically to the dark palette on watchOS** — there's no light appearance and no `UITraitCollection` there. Appearance in Settings is iOS-only by the same logic; don't "fix" it.
- **Motion lives in `TimerView.ActiveFastContent`** (§5): launch fill 1.8s, ignite 0.9s (triggered by the fast being <2s old on appear), a flash + soft haptic at each zone crossing, and the ember burst plus green "Log this fast" CTA at the goal. All of it is skipped under Reduce Motion.

Celebration cues are ≤1.5s, non-blocking, and fall back to a color fade under Reduce Motion.
